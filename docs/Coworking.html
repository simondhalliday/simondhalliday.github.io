Overview 2 / 30

What is Claude Cowork?

  • A persistent workspace: reads and writes files on your computer, executes code, maintains context across sessions
  • Programmable skills: reusable, versioned workflows — built once, invoked by name
  • Installable plugins: a skill bundle packaged and shared — any co-author installs the same library
Not a chatbot. A co-authoring environment that executes work on your behalf — and that you can program.
Principle 3 / 30

The core insight

"Any prompt you will run more than twice
is worth turning into a skill."
  • A skill is a reusable, versioned, programmable workflow
  • Skills compose: the output of one becomes the input of the next
  • Skills are shareable: a co-author runs the same workflow on their chapter
Infrastructure compounds. A prompt is a question. A skill is a procedure.

Frontier 13 / 30

Self-improving skills now live

✦ At Loughborough (March 2026) this was a vision. By April it is running on the UOE MCQ generator.
The mcq-skill-improver skill scores a batch of generated MCQs against a 10-criterion rubric, identifies the failure modes that appear most consistently, and proposes targeted revisions to the mcq-generator skill itself.
  • Each skill run is a draw from a distribution — we want to shift the mean and reduce variance
  • Rubric-based evaluation gives a loss function; iterating on the skill is gradient descent on quality
  • Distractors plausible but unambiguously wrong; reading level appropriate for first-year students
  • Correct answer not conspicuously longer; aligned with a stated learning objective

The self-improvement loop

①Run mcq-generator on a chapter → produce a batch of questions
↓
②mcq-skill-improver scores each question against a 10-criterion rubric
↓
③Identify failure modes: which rubric criteria fail most consistently?
↓
④Revise mcq-generator to address those failure modes → new skill version
↓
⑤Re-run · re-evaluate · track improvement across versions · repeat
The same loop applies to any structured output with a rubric: exercise quality, Insights editorial standards, translated chapter accuracy, empirical activity completeness.

How to design, write, test, and improve a skill from scratch

~ 35 minutes · hands-on · bring a task you do repeatedly

Workshop · Anatomy 18 / 30

What a skill actually is

A skill is a Markdown file with two parts: a YAML header and a prompt body. That's it.

---
name: my-skill-name
description: Use this skill when the user wants to review exercises for a chapter. Triggers: "check the exercises", "audit the problem sets".
---

# Your instructions go here.
# State the goal · list inputs · specify output format
# Give one example of good output
Description field = the trigger. Claude reads it to decide whether to invoke the skill. Write it as a list of natural-language phrases a user might say.
Body = the instruction set. A standing memo to Claude: "whenever this skill is called, here is your job."
Workshop · Design 19 / 30

Before you write a word: three questions

1
What triggers this skill?

Write three sentences a user might actually say to invoke it. If you can't write three, the skill is under-specified. If you can write thirty, it's too broad. Your description field should list these trigger phrases directly.

2
What goes in?

List every file, piece of text, or parameter the skill needs. If something is missing, the skill should know to ask rather than guess. Be specific: "the chapter .docx and the exercise .docx" — not "the chapter."

3
What comes out?

Describe the output format precisely: a Word memo, a CSV, a list of bullet points. If you can't describe the output in two sentences, you're not ready to write the skill yet.

Answer all three before opening a text editor. A skill built without these answers will need to be rewritten from scratch.
Workshop · Rubric 20 / 30

The rubric-first principle

"Write the rubric before you write the skill."

If you don't know what good output looks like, you can't tell whether the skill is working. You'll iterate on vibes — and stop too early.

  • Each criterion must be answerable yes/no from a single output
  • Flags coverage gaps and missing scaffolding; assesses Bloom's level per sub-part
  • Produces a memo a co-author can act on without re-reading the chapter
4–8 rubric criteria is usually right. Fewer: not measuring enough. More: you'll never finish evaluating.
Workshop · Drafting 21 / 30

Writing the first draft

Aim for 200–350 words. You will add detail through iteration — not upfront.

  • Goal statement — one sentence: "Your job is to review the exercises in [chapter] against the chapter content."
  • Inputs — explicit list of what you need; what to ask for if missing
  • Output specification — format, length, where to save
  • One example — a concrete example of a finding at the depth you want
First draft of mcq-reviewer was 180 words. Current version: 640 words. Every word added addressed a specific failure in a real run.
Workshop · Iteration 22 / 30

The build-run-revise cycle

Three to five iterations produces a reliable v1. Each iteration is one run + one targeted edit.

①Run on real content — not a toy example. Synthetic inputs produce misleadingly good results.
↓
②Read against the rubric — systematically, criterion by criterion. Which did it meet? Which did it miss?
↓
③Identify the single most important failure — resist fixing everything at once. One edit per iteration keeps causality clear.
↓
④Edit the skill to address that failure — add a specific instruction, a clarifying example, or a tighter output constraint.
↓
⑤Run again — compare across iterations. Did the failure resolve? Did a new one appear?
"One edit per iteration" is the discipline that makes iteration informative. Change five things at once and you learn nothing about what drove the improvement.
Workshop · Failure modes 23 / 30

Five failure modes to watch for

The vague skill Output is plausible-sounding but not useful — right register, wrong depth. Fix: add one concrete example of a finding at the depth you want.
The format floater Output format varies run to run. Fix: specify format explicitly, including section headings: "always follow this structure."
The over-reacher Skill tries to do too much and does all of it poorly. Fix: split into two skills with a clear handoff. Output of A becomes input of B.
The silent assumption Assumes inputs the user often won't provide. Fix: add: "if [X] is not provided, ask the user for it before proceeding."
The hallucinated figure Reports values from figures it cannot read accurately. Fix: run figure-extractor first; instruct the skill to flag rather than estimate.
How to spot them early Run the skill twice on the same input. Outputs differ significantly → format floater. Thin output → vague. Misses half the rubric → over-reacher.

Workshop · Automation 25 / 30

From rubric to automation

→Score a batch of generated outputs against all rubric criteria — pass/fail with brief justification
→Aggregate across the batch: which criteria fail most consistently? (This is the signal.)
→Propose specific changes to the skill prompt to address those failures

Result so far: distractor plausibility is the most persistent failure. Version 2 will address documented student misconceptions per section.

Not magic. The skill-improver diagnoses; you decide what to change. A systematic diagnosis is far more actionable than reading 20 outputs and forming an impression.
Workshop · Context 26 / 30

Giving your skills persistent context

CLAUDE.md lives in your workspace and loads automatically at the start of every session. Put here:

  • Project terminology conventions — "best-response equilibrium," US spelling, reading level
  • Co-author names and chapter assignments
  • Which skills exist and what they produce
  • File naming conventions the pipeline expects
Skills inherit CLAUDE.md — they don't need to repeat it. Write shared conventions once; every skill uses them automatically.

Workshop · Activity 28 / 30

Design your skill — 10 minutes

Work individually or in pairs. Pick one task you do repeatedly in your editorial or research workflow.

①
Name the task

"I repeatedly have to __________ and it takes me __________ each time." Be specific. "Review a chapter" is too broad. "Check that all cross-references in a chapter point to sections that actually exist" is a skill.

②
Answer the three questions

(a) Three trigger phrases; (b) exact inputs needed; (c) what the output looks like — format, length, where it's saved.

③
Write the rubric — 4–6 criteria

Each criterion must be answerable yes/no from a single output. Avoid vague criteria like "is it high quality."

Share back: one person per group, 90 seconds — what's your skill, and what's your hardest rubric criterion to operationalize?
Takeaways 29 / 30

Three things to take away

1
Claude finds what you can't see at scale.

Inconsistencies, gaps, errors — across chapters, datasets, versions. The gap between what the author intended and what the text actually says. This applies to The Economy just as it applies to UOE.

2
Skills turn prompts into infrastructure that transfers.

Any workflow you repeat is worth systematising. Skills built for a textbook inform skills for a course. A CORE skill library deployed to co-authors worldwide compounds across every subsequent chapter, book, and course that uses CORE materials.

3
The system can improve itself — and it already is.

Rubric-based evaluation and iterative skill revision are running now on UOE. The same approach applies to any structured output: exercises, Insights pieces, translated chapters, empirical activities.
